# Changelog

Усі зміни цього проходу правок: бекенд (`JyskBack`), фронтенд (`Front-end-JYSK`)
та інфраструктура запуску. Формат — за розділами, у кожному пункті вказано,
**що було не так** і **що зроблено**.

## 🔐 Безпека

### Жодного `[Authorize]` у всьому бекенді
**Було:** JWT був налаштований, але не захищав нічого. Будь-хто без токена міг
створювати, редагувати й видаляти товари, категорії та варіанти.
**Стало:** усі мутації каталогу закриті `[Authorize(Roles = "Admin")]`,
відгуки/профіль/замовлення — `[Authorize]`, публічні читання позначені
`[AllowAnonymous]` явно.

| Ендпоінт | Доступ |
|---|---|
| `POST/PUT/DELETE /products`, `/products/{id}/images` | Admin |
| `POST/PUT/DELETE /categories` | Admin |
| `POST/DELETE /products/{id}/variants` | Admin |
| `POST /rooms`, `/collections` та їх `/products` | Admin |
| `GET /orders/all`, `PATCH /orders/{id}/status`, `GET /customers` | Admin |
| `POST /products/{id}/reviews`, `GET/PUT /customers/me`, `/orders` | Авторизований |
| решта `GET` | Публічно |

### Ключ підпису JWT лежав у коді у двох місцях
**Було:** рядок `"SuperSecretJyskKey2026_..."` дублювався в `Program.cs:62` і
`AuthService.cs:15`.
**Стало:** ключ береться з конфігурації (`Jwt:Key`). Development — з
`appsettings.Development.json`, Production — лише зі змінної оточення `Jwt__Key`
або user-secrets. Якщо ключ відсутній або коротший за 32 байти, застосунок
навмисно не стартує. Додано перевірку issuer/audience та `ClockSkew` 1 хв.

### Відгук можна було підписати чужим іменем
**Було:** `POST /products/{id}/reviews` брав `customerId` із тіла запиту.
**Стало:** автор береться з JWT (`ClaimTypes.NameIdentifier`). Поле прибрано з
DTO і з фронтенду — це також привело код у відповідність із контрактом.

### `GET /customers/me` без токена повертав вигаданого користувача
**Було:** запит без авторизації віддавав `200 OK` із «Оленою Ковальчук» —
фронт вважав гостя авторизованим.
**Стало:** `401`. Розбір `Guid.Parse` замінено на `TryParse` в екстеншені
`ClaimsPrincipal.GetUserId()`, щоб кривий токен не валив запит винятком.

### Роль можна було б призначити собі при реєстрації
**Стало:** `RegisterAsync` завжди виставляє `Role = "Customer"`; поле з тіла
запиту не приймається. Email нормалізується до нижнього регістру.

### CORS і HTTPS-редирект
**Було:** `AllowAnyOrigin()` + безумовний `UseHttpsRedirection()`, який у
Development ламав preflight на http-профілі.
**Стало:** список джерел із `Cors:AllowedOrigins`, редирект лише поза
Development.

## 🖥️ Фронтенд

### Баг `categories.filter is not a function`
**Причина:** файла `.env.local` не було, `VITE_API_BASE_URL` дорівнював
`undefined`, `baseURL` ставав порожнім — запити летіли на origin самого Vite і
поверталися HTML-сторінкою. Стор писав цей HTML у `categories`, а рендер
викликав на ньому `.filter`.
**Виправлено трьома шарами:**
1. `api/axios.js` має явний дефолт `http://localhost:5118/api`;
2. створено `.env.local` (і `start.bat` створює його, якщо немає);
3. усі списки проходять через `asArray()` — навіть за несподіваної відповіді
   в state потрапляє масив, а не рядок.

### Баги роутингу
| Проблема | Виправлення |
|---|---|
| Номер сторінки каталогу жив у локальному стані: кнопка «Назад» у браузері не працювала, посилання на другу сторінку не відкривалось | `?page=` у URL |
| `NavLink` порівнює лише шлях, тому «Каталог» і «Акції» підсвічувались разом | Порівняння з урахуванням query-рядка |
| Банер на головній вів на `/catalog?categoryName=Для саду` — такого фільтра в API немає, відкривався весь каталог | Замінено на робочий фільтр |
| Скрол не скидався при переході: наступна сторінка відкривалась прокрученою вниз | `ScrollToTop` (реагує на зміну шляху, але не на зміну фільтрів) |
| Після редиректу на `/login` гість повертався на головну, а не туди, куди йшов | `state.from` у `RequireAuth` + повернення після входу |

### Кошик і замовлення (раніше — німі кнопки)
**Було:** іконка кошика в шапці й кнопка «Додати в кошик» на картці товару
не мали обробників взагалі. Купити було неможливо.
**Стало:**
- `stores/cartStore.js` — кошик у `localStorage` (у бекенда немає ресурсу
  `/cart`, замовлення створюється одним `POST /orders`); різні варіанти
  одного товару — різні рядки
- `stores/wishlistStore.js` — обране
- `stores/orderStore.js` — мої замовлення, деталі, оформлення, адмінський список
- Сторінки: `/cart`, `/checkout`, `/orders`, `/orders/:id`, `/wishlist`,
  `/admin/orders`, `/rooms`, `/rooms/:id`, `/collections`, `/collections/:id`
- Лічильники кошика й обраного в шапці

### Адмінські панелі бачили всі
**Було:** `ProductAdminForm`, `ProductAdminPanel`, `CategoryAdmin` рендерились
будь-якому відвідувачу, включно з гостем.
**Стало:** показуються лише за `customer.role === "Admin"`. Це UX-шар —
доступ усе одно вирішує бекенд.

### Інше
- `RequireAuth` / `RequireAuth adminOnly` для приватних маршрутів
- Профіль: редагування через `PUT /customers/me`
- Єдиний розбір помилок API (`errorMessage`): показує `message` від бекенда,
  текст валідації або підказку «Бекенд недоступний», а не загальну заглушку
- `localStorage` з битим JSON більше не валить застосунок на старті
- `productImage()` розпізнає рядок-заглушку `"placeholder.jpg"` зі старого
  сіда й показує власний плейсхолдер замість «битої» картинки
- Каталог більше не робить два запити на кожну зміну фільтра (у залежностях
  ефекту лежали і `searchParams`, і виведені з нього значення)
- Форми профілю та оформлення заповнюються через `key`-ремонтування, а не
  синхронізацією в `useEffect`, яка перетирала введений текст

## 🖼️ Зображення товарів

### Три посилання на Unsplash віддавали 404
Перевірено всі 21 адресу з сіда й головної сторінки. Мертві замінено:

| Що | Було | Стало |
|---|---|---|
| Журнальний столик GANDRUP | `photo-1533779283484-…` | `photo-1583847268964-…` (світла вітальня з круглим дерев'яним столиком) |
| Крісло офісне TJELE | `photo-1580481072645-…` | `photo-1571624436279-…` (шкіряні офісні крісла) |
| Настільна лампа FREDERIK | `photo-1534105755980-…` | `photo-1519219788971-…` (настільна лампа) |
| Обкладинка колекції «Скандинавський стиль» | той самий мертвий id, що й у столика | `photo-1611269154421-…` (окреме фото, більше не дублює товар) |

### Картинки важили по кілька мегабайтів
**Було:** адреси без query-параметрів — Unsplash віддає оригінал у повному
розмірі. На сторінці каталогу таких було 12 одночасно, тож частина фото
просто не встигала завантажитись.
**Стало:** до всіх адрес додано `?auto=format&fit=crop&w=800&q=80`
(обкладинки кімнат і колекцій — `w=1200`). CDN віддає стиснуту версію
потрібного розміру.

Зміни внесено і в `DbInitializer.cs`, і в наявний `jysk.db` — сід не
перезаписує вже заповнену базу, тому одного правлення коду було б замало.

### Биті посилання більше не показуються як «зламане фото»
Доданий компонент `components/RemoteImage.jsx`: будь-яка помилка завантаження
перемикає картинку на текстовий плейсхолдер. Чужий CDN рано чи пізно
змінить або прибере файл — сторінка від цього псуватись не має.
Застосовано в картці товару, галереї, кошику, деталях замовлення, вітринах
і на головній.

## ⚠️ Що варто знати

1. **`jysk.db` закомічений у репозиторій.** Це не виправлено: прибрати файл із
   історії — окрема операція над git, яку краще робити свідомо
   (`git rm --cached JyskBackend/jysk.db` + запис у `.gitignore`).
2. **Гроші зберігаються як `REAL`.** Для магазину-демо цього достатньо, але для
   реальних розрахунків правильніше зберігати копійки цілим числом.
3. **Пароль адміністратора лежить у `appsettings.json`.** Для Development це
   свідомий компроміс; у Production задавайте `Seed__AdminPassword` змінною
   оточення.
4. **Розбіжності контракту з реальністю.** У прикладах
   `jysk-api-endpoints.md` id товарів і замовлень показані числами
   (`"productId": 5`), хоча в моделі це `Guid`. Реалізація слідує моделі —
   приклади в документі застаріли.
5. **Тестові дані в dev-базі.** Під час перевірки створено товар `Test sofa`
   (знятий з продажу), користувач `ivan@test.ua` і одне замовлення. Щоб почати
   з чистого аркуша — видаліть `JyskBackend/jysk.db`, схема й сід
   відтворяться на старті.
6. **Візуальна перевірка сторінок у браузері не проводилась** — лінтер і збірка
   фронтенда проходять, усі ендпоінти бекенда протестовані запитами.

## ✅ Як перевірялось

**Бекенд** — 20+ запитів до живого API:
вхід адміністратора, `401` для анонімного `POST /products` і `403` для
покупця, валідація тіла (`400`), пагінація з `pageSize=0`, сортування за
ціною й рейтингом, фільтр `roomId`, створення відгуку від імені токена,
оформлення замовлення зі списанням залишку (5 → 3), спроба замовити
99 шт. (`409`), зміна статусу адміністратором (`200`) і покупцем (`403`),
неприпустимий статус (`400`), видалення товару із замовлення (`409`) з
подальшим зникненням його з видачі.

**Фронтенд** — `npm run lint` і `npm run build` без помилок і попереджень.
